# fast_track

HTTP-сервис на Node.js, который отслеживает цены криптовалют через CoinMarketCap Pro API. Сейчас работают конфигурация из окружения, JSON-логи, единый формат ошибок, SQLite с миграциями, CRUD `/api/coins`, ключи API с ролями, текущая цена и история цен. `GET /status` проверяет соединение с базой и в CoinMarketCap не ходит. Фоновая синхронизация цен появится в следующий день. Её настройки уже читаются и проверяются при старте.

## Требования

- Node.js 22.9 или новее. Скрипты `start` и `dev:run` передают окружение через флаг `--env-file-if-exists`, он есть только с этой версии. В корне лежит `.nvmrc` со значением `22`.
- npm.

## Ключ CoinMarketCap

1. Зарегистрируйтесь в Developer Portal: [pro.coinmarketcap.com/signup](https://pro.coinmarketcap.com/signup). Для проверки хватает бесплатного плана Basic.
2. Откройте [pro.coinmarketcap.com/account](https://pro.coinmarketcap.com/account). Ключ лежит в блоке API Key на вкладке Overview. Наведите курсор, чтобы показать его, и скопируйте кнопкой Copy Key.
3. Вставьте ключ в локальный `.env` в поле `CMC_API_KEY`. Файл `.env` в git не попадает. В репозитории остаётся только `.env.example` с плейсхолдером `YOUR_API_KEY`.

Запросы к Pro API пойдут на `https://pro-api.coinmarketcap.com` с заголовком `X-CMC_PRO_API_KEY`. Ключ не пишется в логи и не возвращается в тексте ошибки конфигурации.

## Запуск

```bash
cp .env.example .env
# впишите CMC_API_KEY
npm ci
npm run build
npm start
```

Сервер слушает порт из `PORT` (по умолчанию 3000). Проверка:

```bash
curl -s http://localhost:3000/status
```

Ответ `200` и JSON `{ "status": "ok", "checks": { "db": "ok" }, "uptimeSec", "timestamp", "version" }`. `checks.db` — результат `SELECT 1`. Если база недоступна, ответ `503`: `status` равен `degraded`, `checks.db` равен `error`. Текст ошибки SQLite в тело не попадает, он остаётся в логе. `/status` не обращается к CoinMarketCap. `version` берётся из `package.json`. В ответе есть заголовок `X-Request-Id`. Заголовка `X-Powered-By` нет.

Если порт занят, процесс пишет лог `Server failed to start` и завершается с кодом 1.

### Разработка

Сборка и процесс разнесены по двум командам. В первом терминале:

```bash
npm run dev
```

Это `tsc -p tsconfig.build.json --watch`: при сохранении файлов в `src` обновляется `dist`. Во втором терминале, когда первая сборка уже прошла:

```bash
npm run dev:run
```

Это `node --watch --env-file-if-exists=.env dist/server.js`. Node перезапускает процесс, когда меняется `dist`.

Проверка типов без запуска тестов: `npm run typecheck`.

## Переменные окружения

Пустое значение не подставляется как значение по умолчанию: если переменная задана, она должна быть валидной. Незаданная переменная получает значение из таблицы. Целые числа принимаются только как последовательность цифр, без пробелов, `0x` и экспоненты. `CMC_API_KEY` обрезается по краям.

| Переменная | По умолчанию | Правило |
|---|---|---|
| `NODE_ENV` | `development` | `development`, `production` или `test` |
| `PORT` | `3000` | целое от 1 до 65535 |
| `LOG_LEVEL` | `info` | `error`, `warn`, `info`, `debug`, `silent` |
| `DB_PATH` | `./data/app.db` | непустая строка. Каталог создаётся при старте. `data/` и файлы `*.db` в git не входят |
| `CMC_BASE_URL` | `https://pro-api.coinmarketcap.com` | URL со схемой `http` или `https` |
| `CMC_API_KEY` | нет | обязателен, если `NODE_ENV` не `test`. В тестах можно не задавать |
| `CMC_TIMEOUT_MS` | `5000` | целое от 100 до 60000 |
| `QUOTE_CURRENCY` | `USD` | 3–5 заглавных латинских букв |
| `PRICE_MAX_AGE_MS` | `60000` | целое ≥ 0 |
| `MAX_TRACKED_COINS` | `200` | целое от 1 до 200 |
| `SYNC_INTERVAL_MS` | `300000` | целое ≥ 60000 |
| `SYNC_ENABLED` | `true` | только `true` или `false` |
| `SHUTDOWN_TIMEOUT_MS` | `10000` | целое от 1000 до 60000 |

Неверное значение останавливает процесс до `listen`: в stderr одна строка вида `Invalid env PORT: expected integer 1..65535, got "abc"`, код выхода 1. Для отсутствующего ключа текст такой: `Invalid env CMC_API_KEY: expected non-empty string`. Сам ключ в это сообщение не попадает.

## API-ключи

Маршруты `/api` требуют заголовок `Authorization: Bearer <key>`. Схема `Bearer` не зависит от регистра. Роли две: `read` читает список, одну монету, текущую цену и историю, `admin` делает то же самое и ещё создаёт, изменяет и удаляет монеты.

Ключ создаётся после сборки. В базе остаётся только его sha256-хеш:

```bash
npm run apikey:create -- --name local --role admin
```

Команда печатает секрет один раз и строку `Save this key now. It cannot be shown again.` Показать тот же ключ снова нельзя. Скрипту нужен только `DB_PATH`: `CMC_API_KEY` он не читает.

Отзыв по числовому id строки:

```bash
npm run apikey:revoke -- --id 1
```

## Эндпоинты

`GET /status` открыт без ключа. Запросы к `/api` без годного ключа получают 401 `Invalid or missing API key` и заголовок `WWW-Authenticate: Bearer`. Неверная роль получает 403 `Insufficient permissions` без этого заголовка.

| Метод и путь | Роль | Успех | Отказ |
|---|---|---|---|
| `GET /status` | не нужна | 200, `checks.db` равен `ok` | 503 `degraded`, если база недоступна |
| `GET /api/coins` | `read`, `admin` | 200, страница `{ items, total, limit, offset }` | 401 без ключа; 403 у чужой роли; 400 у кривого query |
| `POST /api/coins` | `admin` | 201 и `Location: /api/coins/{SYMBOL}` | 401 без ключа; 403 у чужой роли; 400 валидация; 404 нет в каталоге; 409 дубль или лимит; 502 чужой символ каталога или ошибка запроса к CoinMarketCap; 503, если CoinMarketCap недоступен; 504 таймаут |
| `GET /api/coins/:symbol` | `read`, `admin` | 200, карточка монеты; `btc` находит `BTC` | 401 без ключа; 403 у чужой роли; 400 у символа; 404 нет строки |
| `GET /api/coins/:symbol/price` | `read`, `admin` | 200: цена, `source` (`cache` или `live`), `stale`, `ageSec` | 401 без ключа; 403 у чужой роли; 400 у символа; 404 нет монеты; 502, 503 или 504, если CoinMarketCap не ответил и сохранённой цены нет. Если строка в базе есть, отказ источника отдаёт 200 со `stale: true` |
| `GET /api/coins/:symbol/history` | `read`, `admin` | 200 `{ symbol, quoteCurrency, items, total, limit, offset }`. Пустая история — `items: []`, `total: 0` | 401 без ключа; 403 у чужой роли; 400 у query; 404 нет монеты. В CoinMarketCap маршрут не ходит |
| `PATCH /api/coins/:symbol` | `admin` | 200, `isActive` изменён | 401 без ключа; 403 у чужой роли; 400 у тела; 404 нет строки |
| `DELETE /api/coins/:symbol` | `admin` | 204 без тела | 401 без ключа; 403 у чужой роли; 404 нет строки |

`GET /api/coins/:symbol` возвращает карточку монеты, не цену. Цена лежит на `/price`.

## CoinMarketCap

Процесс создаёт один `CmcClient` и передаёт его в `CoinsService` как каталог и в `PricesService` как источник котировок. Запросы идут на `CMC_BASE_URL` (по умолчанию `https://pro-api.coinmarketcap.com`) с заголовком `X-CMC_PRO_API_KEY` и таймаутом `CMC_TIMEOUT_MS`.

| Эндпоинт CMC | Когда вызывается | Кредиты плана |
|---|---|---|
| `GET /v1/cryptocurrency/map` | `POST /api/coins`, параметр `symbol` | 0. Документация Pro API прямо говорит, что кредит за этот вызов не списывается |
| `GET /v3/cryptocurrency/quotes/latest` | текущая цена устарела | 1 кредит на каждые 250 возвращённых монет, округление вверх, и ещё 1 кредит на каждую валюту `convert` после первой |

Цифры взяты из справочника Pro API (раздел Cryptocurrency, сентябрь 2026). Мы передаём одну валюту, `QUOTE_CURRENCY` (по умолчанию `USD`), и `skip_invalid=true`. Обновление одной монеты или пачки до 250 монет стоит 1 кредит. Больше 200 id за один запрос клиент не отправляет. Пустой список id в сеть не уходит.

`/price` при `PRICE_MAX_AGE_MS=60000` обращается к CoinMarketCap не чаще одного раза в минуту на монету. Пока `now - fetched_at` строго меньше этого окна, ответ берётся из базы и `source` равен `cache`. Тысяча запросов в час к одной монете — это не больше 60 вызовов quotes и не больше 60 кредитов в час. Поиск монеты через map кредит не тратит.

В `debug`-лог успешного запроса пишется `creditCount` из `status.credit_count`. Ключ в лог, в текст ошибки и в тело ответа не попадает.

Параметр `listing_status` не отправляется: справочник всё равно возвращает неактивные строки. Клиент оставляет строки с `is_active === 1` и тем же символом. Символ приводится к верхнему регистру.

Тикер в CoinMarketCap не уникален. Среди активных совпадений выбирается монета с наименьшим `rank`: это наибольшая капитализация. Строка с `rank: null` идёт последней. Если наименьший rank у нескольких строк или rank нет ни у одной, остаётся первая строка ответа. В нашу таблицу пишется её `cmcId`, его же видит клиент в карточке монеты. Неизвестный символ — это HTTP 400 с текстом `Invalid value for "symbol"`. Для map такой ответ значит «монеты нет»: `POST /api/coins` отвечает 404, а не 502.

## Тесты

Ключ CoinMarketCap для тестов не нужен: `tests/setup.ts` выставляет `NODE_ENV=test` и `LOG_LEVEL=silent`. Тесты не вызывают `pro-api.coinmarketcap.com`. Тела ответов лежат в `tests/fixtures/cmc`, HTTP-клиент получает фейковый адаптер, один таймаут проверяется локальным сервером, который не отвечает.

```bash
npm test
npm run test:coverage
```

Покрытие считается по `src/**/*.ts`, кроме `src/server.ts`: этот файл только запускает процесс.

## Принятые решения

- **Node 22.9+.** Флаг `--env-file-if-exists` не требует отдельного пакета для `.env`. Версия зафиксирована в `engines` и `.nvmrc`. Типы `@types/node` стоят на ветке 22, чтобы компилятор не разрешал API новее рантайма.
- **Один TypeScript 6.** `tsc` и ts-jest используют один и тот же пакет `typescript`. Нативный TypeScript 7 не подходит: у него нет стабильного compiler API, который ждёт ts-jest.
- **CommonJS и `moduleResolution: nodenext`.** Относительные импорты в исходниках заканчиваются на `.js`. Jest сопоставляет такой суффикс с `.ts` через `moduleNameMapper`.
- **Express 5.** Приложение собирается в `createApp` и само не слушает порт. Слушает только `src/server.ts`. Ошибка `listen`, например занятый порт, завершает процесс с кодом 1. Иначе Docker с `restart: on-failure` решит, что сервис поднялся.
- **Остановка по таймауту.** SIGINT и SIGTERM сначала закрывают HTTP-сервер и простаивающие keep-alive соединения, затем остальные ресурсы. Пул CoinMarketCap уничтожается до базы: `closeCmcHttp` вызывает `destroy()` у http- и https-агентов. База закрывается последней: пока сервер дорабатывает запросы, она им нужна. Если за `SHUTDOWN_TIMEOUT_MS` соединения ещё живы, процесс рвёт их, закрывает ресурсы в `try/catch` и выходит с кодом 1. `uncaughtException` и `unhandledRejection` идут в ту же остановку. Ошибка открытия базы или миграции пишется в лог, открытое соединение закрывается, и процесс выходит с кодом 1 до `listen`.
- **Свои валидаторы и логгер.** Отдельные библиотеки для конфига и логов не подключались. Лог — одна JSON-строка. Логгер не бросает исключения: циклы, `bigint`, глубина и `toJSON` обрабатываются внутри. Поля с `apikey`, `secret`, `token`, `password` или `authorization` в имени заменяются на `[REDACTED]`.
- **Один формат ошибок.** Тело ответа: `{ "error": { "code", "message", "requestId" } }`. Детали валидации добавляются только когда они есть. Внутренний текст и stack клиенту не отдаются. `errorHandler` подробно логирует только 5xx. Каждый запрос один раз пишет `requestLogger`, для 4xx туда же попадает `errorCode`.
- **`X-Request-Id`.** Клиентский заголовок принимается, если это 1–128 символов из латиницы, цифр, точки, `_` и `-`. Иначе сервер ставит UUID. Идентификатор возвращается в ответе и в логе.
- **Версия из `package.json`.** `server.ts` читает файл через `fs` и передаёт версию в `createApp`. Импорт JSON из `src` сломал бы сборку из-за `rootDir`. В тестах версию можно подменить.
- **Драйвер SQLite — `better-sqlite3`.** К базе нужен драйвер, а не ORM: запросы остаются сырым SQL. Синхронный API здесь уместен, запрос локальный и короткий. Есть `transaction()` и типизированный `SqliteError`. Встроенный `node:sqlite` на линии Node 22 всё ещё экспериментальный и печатает `ExperimentalWarning`, поэтому при `engines` `>=22.9` берём стабильный пакет. `openDb(filePath)` создаёт каталог, открывает файл и на каждом соединении ставит `foreign_keys = ON`, `journal_mode = WAL` и `busy_timeout = 5000`. Внешние ключи в обычной сборке SQLite выключены, и без pragma `ON DELETE CASCADE` молча не работает. Явная установка не зависит от флагов сборки драйвера. WAL позволяет читать, пока фоновая синхронизация пишет. Экземпляр передаётся в конструкторы. Синглтона на уровне модуля нет: у каждого теста своя база.
- **Файл базы, в том числе в тестах.** Каталог `data/` в git не входит. Тесты создают файл во временной папке и проверяют WAL и файловые блокировки. Память `:memory:` для данных не используем.
- **Миграции — модули TypeScript в одной `IMMEDIATE`-транзакции.** `tsc` не копирует `.sql` в `dist`, отдельное копирование для сборки и Docker не нужно. Модуль экспортирует `{ name, up }`, список миграций явный и идёт по порядку. Имена уникальны и строго возрастают, иначе старт падает до применения. После этой проверки весь `migrate` идёт в `db.transaction(...).immediate()`. `BEGIN IMMEDIATE` сразу берёт блокировку записи, и список уже применённых миграций читается внутри неё. Второй процесс на том же файле ждёт `busy_timeout` (5000 мс) и после входа видит, что миграции уже есть. `BEGIN DEFERRED` откладывает блокировку до первой записи, поэтому оба процесса успевали прочитать пустой `schema_migrations` и второй падал на `CREATE TABLE`. `BEGIN EXCLUSIVE` запретил бы и чтение; для миграций достаточно блокировки записи. Если SQL в этом запуске падает, откатывается вся транзакция: раньше применённые миграции остаются, новые из этого вызова — нет. Применённую миграцию не меняют: новая схема — новая миграция. При старте `openDb` и `migrate` выполняются до `listen`.
- **Поля схемы `001_init`.** `cmc_id` лежит рядом с `symbol`: тикер в CoinMarketCap не уникален и может смениться, а id источника стабилен. `source_updated_at` — момент котировки у CoinMarketCap, `fetched_at` — момент, когда строку записал наш сервис. Уникальность `(coin_id, quote_currency, source_updated_at)` хранит одну строку на одну котировку источника. `fetched_at` в ключ не входит. Повторный опрос с тем же временем источника не создаёт вторую строку: `INSERT OR IGNORE` находит дубль и обновляет только `fetched_at`. Цена и остальные поля котировки остаются записанными раньше. Даты — TEXT в ISO 8601 UTC, всегда `toISOString()` и суффикс `Z`: в этом виде лексикографический порядок совпадает с хронологическим. Последняя цена читается как `ORDER BY source_updated_at DESC LIMIT 1`. План `EXPLAIN` для этого запроса — `SEARCH prices USING INDEX sqlite_autoindex_prices_1 (coin_id=? AND quote_currency=?)`: это тот же UNIQUE, временного b-tree нет. Индекс истории начинается с `coin_id`, потому что запрос читает одну монету, затем валюту, затем время. Отдельный индекс с теми же колонками не создаётся.
- **Удаление и пауза — разные операции.** `DELETE` стирает строку, история цен уходит через `ON DELETE CASCADE`. Пауза — это `PATCH` поля `is_active`: монета остаётся в таблице.
- **В URL монета ищется по `symbol`.** В нашей таблице символ уникален: `/api/coins/BTC`. Регистр приводим к верхнему, `btc` сохраняется как `BTC`. Рядом хранится `cmc_id`: тикер в CoinMarketCap не уникален, а числовой id источника стабилен.
- **В ответе монеты нет внутреннего `id`.** Клиент получает `symbol`, `cmcId`, `name`, `slug`, `isActive`, `createdAt` и `updatedAt`. Числовой id строки остаётся в базе. `cmcId` в теле показывает, какую запись CoinMarketCap выбрал каталог: тикер может смениться, id источника стабилен.
- **Ключ API — `ft_` и sha256.** Формат: `ft_` + `randomBytes(32).toString('base64url')`. Префикс виден в утёкшем конфиге и в secret scanning. В базе лежит только hex-хеш sha256. У ключа 256 бит энтропии, перебор нереален, активный ключ находится одним запросом по уникальному индексу.
- **Поиск ключа по хешу, без `timingSafeEqual`.** Аутентификация считает sha256 и ищет строку по уникальному индексу `key_hash`. Это не посимвольное сравнение секрета в JavaScript: атакующий меняет вход хеш-функции, а не подбирает совпадающий префикс по времени ответа. Отозванный ключ (`revoked_at IS NOT NULL`) не проходит.
- **Одинаковый ответ на любой отказ ключа.** Нет заголовка, чужая схема, пустой токен, неизвестный и отозванный ключ дают 401, заголовок `WWW-Authenticate: Bearer` и одно сообщение `Invalid or missing API key`. Причина пишется в warn-лог без самого ключа и без его хеша. Схема `Bearer` сравнивается без учёта регистра.
- **`last_used_at` не чаще раза в минуту.** Иначе каждый успешный запрос писал бы в базу и раздувал WAL. Для аудита достаточно знать, что ключ был жив в эту минуту. Если `last_used_at` пустой или старше 60 секунд, middleware его обновляет. В лог запроса добавляется `keyName` — имя ключа, не секрет.
- **Каталог и котировки — два интерфейса, один клиент.** `CoinsService` спрашивает `CoinCatalog`, `PricesService` спрашивает `PriceProvider`. Добавление монеты не читает цену, история не ходит в сеть. `CmcClient` реализует оба интерфейса, и процесс передаёт один экземпляр в оба сервиса. Тесты подставляют фейки и не ходят в сеть.
- **Повтор только у идемпотентного сбоя.** Таймаут (`ECONNABORTED`, `ETIMEDOUT`), сеть без ответа (`ECONNRESET`, `ENOTFOUND`, `ECONNREFUSED`, `EAI_AGAIN`) и HTTP 5xx повторяются. Паузы 200 мс, затем 400 мс, всего три попытки. 4xx и 429 не повторяются: повтор не изменит ответ, а лимит только усилится. Пока попытки остаются, сбой пишется как `warn`. После последней — `error`. Отмена через `AbortSignal` (`ERR_CANCELED`) не превращается в ошибку API и не повторяется.
- **Соединения CoinMarketCap держатся.** У axios-инстанса свои `http.Agent` и `https.Agent` с `keepAlive` и `maxSockets: 10`. Следующий запрос переиспользует TCP и TLS и не платит рукопожатие заново. `validateStatus` всегда истинен: HTTP-статус и `status.error_code` разбираются в одном месте.
- **Ошибки CoinMarketCap мапятся в ошибки приложения.** Текст от CoinMarketCap клиенту не отдаётся. В лог 5xx попадают путь без query, HTTP-статус, код и сообщение CoinMarketCap, номер попытки. Конфиг axios, заголовки и ключ туда не кладутся. 401, 402 и 403 — это наш ключ или план, не ключ вызывающего. Если отдать 401, клиент решит, что виноват его `Authorization`. Минутный лимит 1008 можно переждать, поэтому есть `Retry-After` и отдельный код. Дневной, месячный и IP-лимит сразу не отпускает, повтор в том же процессе бесполезен, поэтому это `EXTERNAL_API_UNAVAILABLE` без паузы.

| Что пришло | Повтор | Клиенту | Код |
|---|---|---|---|
| Таймаут | да | 504 `CoinMarketCap request timed out` | `EXTERNAL_API_TIMEOUT` |
| Сеть без ответа | да | 502 `CoinMarketCap is unavailable` | `EXTERNAL_API_ERROR` |
| HTTP 5xx | да | 502 `CoinMarketCap is unavailable` | `EXTERNAL_API_ERROR` |
| 429 и код 1008, минутный лимит | нет | 503 `CoinMarketCap rate limit exceeded`, заголовок `Retry-After: 60` | `EXTERNAL_API_RATE_LIMITED` |
| 429 и код 1009, 1010 или 1011 (день, месяц, IP) | нет | 503 `CoinMarketCap is unavailable` | `EXTERNAL_API_UNAVAILABLE` |
| 401, 402, 403 | нет | 503 `CoinMarketCap is unavailable` | `EXTERNAL_API_UNAVAILABLE` |
| HTTP 400, кроме неизвестного символа на map | нет | 502 `CoinMarketCap is unavailable` | `EXTERNAL_API_ERROR` |
| HTTP 200, но `error_code` не 0 или тело не читается | нет | 502 `CoinMarketCap is unavailable` | `EXTERNAL_API_ERROR` |

- **Свежесть считается по `fetched_at`.** `source_updated_at` — время котировки у CoinMarketCap. К моменту ответа оно уже может быть старше `PRICE_MAX_AGE_MS`, и проверка по нему промахивалась бы мимо только что сохранённой строки. Свежая цена: `now - fetchedAt < priceMaxAgeMs`. Равенство окна — уже устарело. `ageSec` — целые секунды с `fetched_at`, не меньше нуля. Ответ `/price` затем читается из базы заново: если источник прислал ту же метку времени, клиент видит сохранённую цену, а не число из последнего ответа.
- **Отказ CoinMarketCap не стирает последнюю цену.** `ExternalApiError` при уже сохранённой строке отдаёт её с `source: cache` и `stale: true` и пишет warn `Serving a stale coin price`. Другая ошибка наружу пробрасывается, даже если строка есть. Если строки нет, клиент получает 502, 503 или 504 этого вызова. Цена живёт в SQLite, а не в переменной процесса: её видит следующий процесс после рестарта.
- **Одновременные устаревшие запросы ходят в CoinMarketCap каждый сам.** Общий in-flight промис в памяти процесса не хранится. Это thundering herd: пачка запросов в одну секунду после истечения окна делает пачку одинаковых вызовов. Его закроет фоновая синхронизация следующего дня, которая будет держать кеш тёплым одним batch-запросом.
- **История фильтруется по времени источника и не ходит в сеть.** `from` и `to` включительны и сравниваются с `source_updated_at`. Дата без времени, `YYYY-MM-DD`, — это полночь UTC: `2026-10-08` становится `2026-10-08T00:00:00.000Z`, поэтому `to=2026-10-08` не включает более поздние моменты этого дня. Дата с временем принимается только с суффиксом `Z`. Сломанный календарь вроде `2026-02-31` — 400 `must be an ISO date`. `from` позже `to` — 400 на поле `from`. `limit` от 1 до 1000, по умолчанию 100. `offset` от 0. `order` — `asc` или `desc`, по умолчанию `desc`. Неизвестное поле query — 400.
- **Лимит отслеживаемых монет — 409, и проверяется дважды.** Ранний `count()` до каталога экономит кредит CoinMarketCap, когда лимит уже занят. Он не гарантия: `await` отдаёт цикл событий, и второй запрос успевает пройти ту же проверку. Окончательно лимит держит один statement `INSERT ... SELECT ... WHERE (SELECT COUNT(*) FROM coins) < @maxCoins`. В SQLite такой statement атомарен, а better-sqlite3 выполняет его синхронно, поэтому между подсчётом и вставкой никто не вклинится. Пустой `RETURNING` — это лимит, `SQLITE_CONSTRAINT_UNIQUE` — дубль. Оба ответа 409 с разными сообщениями. Отказ зависит от текущего числа строк и снимается после удаления монеты. 400 оставлен для сломанного запроса, 422 — для тела, которое неверно само по себе.
- **Скрипт ключей читает только путь к базе.** `loadDbConfig` проверяет `DB_PATH` теми же правилами, что и `loadConfig`. `withAppDatabase` вызывает только её. Ключ CoinMarketCap скрипту не нужен: он его не использует.
- **Чужой символ каталога — 502.** Если на запрос `ABC` каталог вернул монету с другим тикером, сервис бросает `ExternalApiError` с кодом `EXTERNAL_API_ERROR`. Сравнение без учёта регистра: `btc` и `BTC` — одна монета, в строку пишется символ каталога. Строка не создаётся, когда тикеры различаются. Запрошенный и полученный символы попадают в `context` лога, не в тело ответа. Смена тикера у источника — не повод записать другую монету.
